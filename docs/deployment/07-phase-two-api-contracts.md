# فاز ۲ — قرارداد API و اعتبارسنجی ورودی‌ها

وضعیت: در حال اجرا؛ لایه قرارداد و endpointهای اصلی پیاده‌سازی شده‌اند، تست یکپارچه واقعی با MySQL هنوز باقی است.

## قرارداد خطای مشترک

تمام خطاهای API کسب‌وکاری از قالب زیر استفاده می‌کنند:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "اطلاعات ارسالی معتبر نیست.",
    "details": {
      "capacity": ["مقدار باید بزرگ‌تر از صفر باشد."]
    },
    "correlationId": "8c42ccbe-..."
  }
}
```

مقدار `correlationId` در هدر `x-correlation-id` نیز برگردانده می‌شود. شناسه معتبر ورودی حفظ و در غیر این صورت شناسه جدید ساخته می‌شود. خطاهای داخلی و متن Prisma به client ارسال نمی‌شوند.

کدهای تثبیت‌شده:

- `INVALID_JSON`
- `VALIDATION_ERROR`
- `UNAUTHORIZED`
- `FORBIDDEN`
- `NOT_FOUND`
- `CONFLICT`
- `BUSINESS_RULE_VIOLATION`
- `INTERNAL_ERROR`

## پوشش schemaها

Zod در مرز API برای payloadهای زیر فعال است:

- طرف قرارداد و دارایی؛
- درخواست، تکمیل اطلاعات و بررسی درخواست؛
- ایجاد، یادداشت و پذیرش/رد پیشنهاد؛
- ایجاد، پیکربندی و امضای قرارداد؛
- کنتور و قرائت کنتور؛
- طرح قیمت‌گذاری و محاسبه قیمت؛
- محاسبه و تغییر وضعیت تسویه؛
- صدور و تغییر وضعیت صورتحساب؛
- upload، تأیید و حذف مدرک؛
- تغییر وضعیت اعلان.

schemaها `strict` هستند؛ فیلد ناشناخته رد می‌شود و payload خام مستقیماً به Prisma نمی‌رسد.

قواعد بین‌فیلدی شامل ترتیب تاریخ‌ها، عدد مثبت/غیرمنفی، شماره موبایل ایران، درصد ۰ تا ۱۰۰، مجموع ۱۰۰ درصدی سهم ثابت و بازار، مجموع سهم دارایی‌های قرارداد، ظرفیت قابل فروش و سازگاری انرژی خام/پذیرفته/ردشده است.

شناسه‌های مرجع پیش از mutation برای Party، Asset، Meter، Request، Proposal، Contract، PricingPlan و Settlement بررسی می‌شوند.

## pagination

- مقدار پیش‌فرض `page=1` و `limit=20` است.
- `page` عدد صحیح حداقل ۱ و حداکثر ۱۰۰٬۰۰۰ است.
- `limit` عدد صحیح بین ۱ و ۱۰۰ است.
- لیست دارایی، طرف، درخواست، پیشنهاد، قرارداد، کنتور، قرائت، تسویه، صورتحساب، نرخ‌نامه و اعلان محدود شده است.

## تطبیق UI و backend

ناسازگاری‌های زیر برطرف شدند:

- `POST /api/proposals` برای ساخت پیشنهاد؛
- `PATCH /api/proposals` برای پذیرش یا رد توسط مشتری؛
- `DELETE /api/documents/:id` برای حذف مدرک؛
- `PATCH /api/requests/:id` برای اتصال دارایی هنگام تکمیل اطلاعات؛
- `PATCH /api/contracts` برای امضای قرارداد متعلق به مشتری.

UI پیام اصلی یا اولین خطای فیلدی پاسخ API را نمایش می‌دهد.

## semantics تکرار عملیات

| عملیات | رفتار تکرار |
|---|---|
| ساخت پیشنهاد برای درخواست دارای پیشنهاد `PENDING` | پیشنهاد موجود با `200` برگردانده می‌شود. |
| پذیرش/رد دوباره همان پیشنهاد | وضعیت یکسان replay و با `200` برگردانده می‌شود؛ تغییر وضعیت terminal با `409` رد می‌شود. |
| ساخت قرارداد از `requestId` دارای قرارداد | قرارداد موجود با `200` برگردانده می‌شود. |
| محاسبه مجدد تسویه برای قرارداد/دارایی/بازه یکسان | تسویه موجود با `idempotentReplay=true` و `200` برگردانده می‌شود. |
| صدور دوباره صورتحساب برای یک تسویه | صورتحساب موجود با `200` برگردانده می‌شود. |
| ایجاد مستقیم Party، Asset، Meter، Request یا Contract | non-idempotent است؛ client نباید بدون تأیید نتیجه retry خودکار انجام دهد. |
| قرائت تکراری دارایی و شروع دوره | قید unique دیتابیس به `409 CONFLICT` نگاشت می‌شود. |
