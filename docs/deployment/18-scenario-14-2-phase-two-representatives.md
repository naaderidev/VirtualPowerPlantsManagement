# گزارش فاز دو سناریوی ۱۴.۲ - مدیریت نمایندگان شرکت

## ۱. هدف و نتیجه

فاز دو امکان اتصال حساب «نماینده فروشنده» به یک شرکت حقوقی را برای مدیر اصلی فراهم می‌کند. این اتصال بازه اعتبار، مرجع اختیار، یادداشت داخلی و مجوز مستقل امضای قرارداد دارد و بدون حذف سابقه قابل لغو است.

این فاز هیچ شرکت، نیروگاه، قرارداد یا رابطه‌ای را seed نمی‌کند؛ بنابراین اصل «دیتابیس دامنه خالی و فقط هشت کاربر seed‌شده» حفظ شده است.

## ۲. مدل اختیار

- رابطه `REPRESENTATIVE` مجوز فعالیت نماینده به نام شرکت است.
- رابطه `AUTHORIZED_SIGNATORY` مجوز مستقل امضای قرارداد است.
- اعطای اختیار امضا بدون `authorityReference` پذیرفته نمی‌شود.
- بازه‌های هم‌پوشان برای یک نماینده و یک شرکت پذیرفته نمی‌شوند.
- رابطه آینده، جاری، منقضی و لغوشده به‌ترتیب با وضعیت‌های `SCHEDULED`، `CURRENT`، `EXPIRED` و `REVOKED` نمایش داده می‌شود.
- لغو نمایندگی، رابطه متناظر اختیار امضا را نیز لغو می‌کند؛ رکوردها برای ممیزی حذف نمی‌شوند.
- فقط نقش `ADMIN` به صفحه و API مدیریت نمایندگان دسترسی دارد.

## ۳. رابط مدیریتی

مسیر `/admin/representatives` به منوی مدیر اصلی اضافه شد و شامل موارد زیر است:

- وضعیت خالی و راهنمای ایجاد نخستین شرکت حقوقی؛
- انتخاب حساب نماینده و شرکت فعال؛
- ثبت شروع و پایان اعتبار؛
- فعال‌سازی اختیار امضا همراه با مرجع اختیار؛
- فیلتر بر اساس وضعیت؛
- ویرایش بازه و حدود اختیار؛
- لغو نرم و قابل ممیزی؛
- نمایش ثبت‌کننده، شماره همراه و مرجع اختیار؛
- چیدمان واکنش‌گرا برای موبایل و دسکتاپ.

اگر حساب نماینده هنوز Party شخصی نداشته باشد، در نخستین تخصیص یک Party نوع `PERSON` به‌صورت تراکنشی برای همان کاربر ساخته و متصل می‌شود. این رفتار هنگام seed اجرا نمی‌شود.

## ۴. قرارداد API

| مسیر | متد | کاربرد |
|---|---|---|
| `/api/representatives` | `GET` | فهرست، گزینه‌های فرم و pagination محدود |
| `/api/representatives` | `POST` | ثبت نمایندگی و اختیار امضای اختیاری |
| `/api/representatives/:id` | `PATCH` | تغییر بازه، مرجع، یادداشت و اختیار امضا |
| `/api/representatives/:id` | `DELETE` | لغو idempotent نمایندگی و اختیار امضای متناظر |

تمام payloadها قبل از Prisma با Zod اعتبارسنجی می‌شوند. عملیات نوشتن با transaction سطح `Serializable`، AuditLog و Notification اجرا می‌شود. پاسخ خطا از قرارداد استاندارد پروژه و correlation ID استفاده می‌کند و متن exception داخلی به client ارسال نمی‌شود.

## ۵. پوشش تست

- تست دامنه برای تشخیص وضعیت، هم‌پوشانی و تطبیق بازه رابطه‌ها؛
- تست schema برای ترتیب تاریخ و الزام مرجع اختیار امضا؛
- تست قرارداد وجود متدهای API؛
- تست دسترسی منو و مسیر برای مدیر و عدم نمایش برای سایر نقش‌ها؛
- typecheck کامل پروژه؛
- lint بدون خطا؛ هشدارهای موجود پروژه از سقف تثبیت‌شده کمتر هستند.

## ۶. معیار خروج

- مدیر می‌تواند نماینده را فقط به شرکت فعال متصل کند.
- اعتبار رابطه در سمت server کنترل می‌شود.
- اختیار فعالیت و اختیار امضا از یکدیگر مستقل‌اند.
- تاریخچه لغو و ویرایش قابل ممیزی است.
- نماینده از ثبت، تغییر و لغو رابطه Notification دریافت می‌کند.
- وضعیت خالی بدون داده ساختگی قابل ارائه است.

نتیجه: فاز دو سناریوی ۱۴.۲ از نظر کد، قرارداد API و کنترل دسترسی تکمیل شده و سیستم برای فاز انتخاب Party فعال توسط نماینده آماده است.
