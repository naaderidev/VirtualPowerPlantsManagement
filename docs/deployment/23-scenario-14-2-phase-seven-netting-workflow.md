# گزارش فاز هفت سناریوی ۱۴.۲ - موتور خالص‌سازی و تأیید دوگانه

## ۱. نتیجه

گردش عملیاتی خالص‌سازی برای قرارداد مادر چندنیروگاهی اجرا شد. یک batch فقط از حداقل دو Settlement تأییدشده، هم‌دوره، هم‌ارز، متعلق به شرکت و گروه یکسان و مربوط به Assetهای متفاوت ساخته می‌شود. نتیجه تا پیش از تأیید مستقل مالی و حقوقی پیش‌نویس است.

## ۲. گروه خالص‌سازی

- ایجاد گروه فقط توسط `ADMIN` انجام می‌شود.
- Party گروه از فروشنده قرارداد روی server استخراج می‌شود و از payload خام client پذیرفته نمی‌شود.
- قرارداد باید فعال، چندنیروگاهی، دارای برنامه مستقل برای همه Assetها و دارای `nettingEnabled=true` در قرارداد و scheduleها باشد.
- ارز گروه از برنامه‌های تجاری قرارداد استخراج می‌شود و همه برنامه‌ها باید ارز یکسان داشته باشند.
- بازه اعتبار گروه از قرارداد مادر گرفته می‌شود.
- اتصال قرارداد به گروه و AuditLog در یک transaction انجام می‌شود.

## ۳. ساخت batch

- feature flag با `NETTING_ENABLED=true` در محیط دمو محلی فعال شد؛ مقدار پیش‌فرض نمونه محیط همچنان `false` است.
- ایجاد batch برای `ADMIN` و `STAFF_FINANCIAL` مجاز است.
- فقط Settlementهای `CONFIRMED` و استفاده‌نشده در UI نمایش داده می‌شوند.
- API مجدداً وضعیت، Party، قرارداد، فعال‌بودن netting، ارز، دوره، Asset متمایز و مبلغ صحیح ریالی را کنترل می‌کند.
- کلید idempotency یکتا است و retry همان درخواست، batch موجود را بدون ایجاد مبلغ یا رکورد تکراری برمی‌گرداند.
- `eligibilityLockKey` یکتا هر Settlement را هنگام ساخت batch رزرو می‌کند و جلوی ورود هم‌زمان به batch دیگر را می‌گیرد.
- در صورت رد یا لغو batch، lock اقلام آزاد می‌شود؛ در batch تأییدشده lock باقی می‌ماند.
- snapshot شامل گروه، دوره، جمع‌ها، شناسه و شماره قرارداد، Asset، Settlement، جهت، مبلغ و snapshot محاسبه اصلی است.

## ۴. محاسبه

- جهت مبلغ نسبت به Party گروه از نقش قرارداد تعیین می‌شود: فروشنده `RECEIVABLE` و خریدار `PAYABLE`.
- جمع دریافتنی و پرداختنی با Decimal محاسبه می‌شوند.
- مبلغ خالص برابر `totalReceivable - totalPayable` است.
- ریز `NettingItem`ها و snapshot مبلغ Settlementهای مبنا بعد از تأیید نیز باقی می‌ماند.

## ۵. گردش تأیید

1. batch با وضعیت `DRAFT` ساخته می‌شود.
2. ایجادکننده مجاز آن را به `FINANCIAL_REVIEW` می‌فرستد.
3. فقط حساب `STAFF_FINANCIAL` می‌تواند تصمیم مالی ثبت کند.
4. تأیید مالی batch را به `LEGAL_REVIEW` می‌برد.
5. فقط حساب `STAFF_LEGAL` می‌تواند تصمیم حقوقی ثبت کند.
6. API متفاوت‌بودن reviewer مالی و حقوقی را داخل transaction کنترل می‌کند.
7. تنها تأیید حقوقی پس از تأیید مالی وضعیت را به `APPROVED` می‌رساند و `approvedAt` را ثبت می‌کند.
8. رد در هر مرحله، دلیل اجباری، AuditLog و آزادسازی lockها را به همراه دارد.

`ADMIN` نمی‌تواند به‌جای دو نقش تخصصی تأیید نهایی را انجام دهد؛ بنابراین ارائه باید واقعاً با دو حساب کارشناس مالی و کارشناس حقوقی انجام شود.

## ۶. رابط کاربری و دسترسی

- صفحه `/admin/netting` به داشبورد عملیاتی سه‌بخشی تبدیل شد: ایجاد گروه، انتخاب اقلام و گردش تأیید.
- دکمه‌ها متناسب با نقش و وضعیت batch نمایش داده می‌شوند.
- `STAFF_LEGAL` منوی خالص‌سازی را می‌بیند، اما به تسویه‌ها، پرداخت‌ها و سایر صفحات مالی دسترسی نمی‌گیرد.
- وضعیت خالی برای نبود گروه، نبود Settlement واجد شرایط و نبود batch مدیریت شده است.
- جزئیات هر batch شامل جمع دریافتنی، پرداختنی، مبلغ خالص، ریز نیروگاه‌ها و نام هر دو reviewer است.

## ۷. دیتابیس و seed

مدل‌های `NettingGroup`، `NettingBatch`، `NettingItem` و `NettingApproval` و قیود لازم در migration فاز یک ایجاد شده بودند؛ بنابراین فاز هفت migration تازه‌ای نیاز نداشت. هیچ داده دامنه‌ای seed نشد و seed همچنان فقط شامل هشت کاربر نقش‌ها است.

## ۸. پوشش آزمون

- پذیرش دو Settlement تأییدشده هم‌دوره از Assetهای متفاوت؛
- محاسبه دریافتنی، پرداختنی و مبلغ خالص با Decimal؛
- رد Settlement قفل‌شده، تأییدنشده، خارج از گروه، با دوره یا ارز متفاوت؛
- اعتبارسنجی settlementهای تکراری و دلیل رد؛
- ثبت مسیرهای API مورد استفاده UI؛
- دسترسی محدود حقوقی به netting؛
- ۹۸ تست کامل پروژه، typecheck، lint هدفمند، build تولیدی و runtime Next.js.

## ۹. معیار خروج

- [x] batch از حداقل دو Settlement تأییدشده و هم‌دوره ساخته می‌شود.
- [x] Party، ارز، Asset متمایز، عضویت گروه و فعال‌بودن netting enforce می‌شوند.
- [x] retry ساخت batch داده یا مبلغ تکراری ایجاد نمی‌کند.
- [x] یک Settlement نمی‌تواند هم‌زمان یا پس از قطعیت در batch دیگری استفاده شود.
- [x] نتیجه پیش از تأیید دوگانه پیش‌نویس باقی می‌ماند.
- [x] تأیید مالی و حقوقی فقط با دو حساب تخصصی و متفاوت انجام می‌شود.
- [x] snapshot و ریز Settlementهای مبنا حفظ می‌شود.
- [x] محاسبه، تغییر وضعیت و تصمیم‌ها AuditLog دارند.
- [x] feature flag خاموش تمام mutationهای netting را متوقف می‌کند.

نتیجه: فاز هفت سناریوی ۱۴.۲ تکمیل است. فاز هشت باید نمایش نتیجه خالص در scope نماینده شرکت و اتصال نتیجه تأییدشده به سند مالی و پرداخت را اجرا کند.
