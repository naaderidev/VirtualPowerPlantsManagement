# گزارش فاز سه سناریوی ۱۴.۲ - انتخاب شرکت طرف فعالیت

## ۱. نتیجه

نماینده فروشنده اکنون پیش از مشاهده یا اجرای فرایندهای مشتری باید یکی از شرکت‌هایی را که نمایندگی معتبر آن‌ها را دارد به‌عنوان Party فعال انتخاب کند. تمام APIهای مشتری پس از انتخاب فقط به همان شرکت scope می‌شوند.

این فاز تغییر schema یا seed ندارد و هیچ شرکت، رابطه، نیروگاه یا قرارداد نمایشی ایجاد نمی‌کند.

## ۲. قرارداد امنیتی

- فهرست شرکت‌های قابل انتخاب فقط از رابطه فعال `REPRESENTATIVE` و بازه معتبر آن استخراج می‌شود.
- شرکت تعلیق‌شده یا غیرفعال قابل انتخاب نیست.
- شناسه انتخاب‌شده با `POST /api/customer/acting-party` ارسال و در server اعتبارسنجی می‌شود.
- انتخاب معتبر در کوکی `HttpOnly`، `SameSite=Lax` و در production با `Secure` نگهداری می‌شود.
- مقدار کوکی در هر درخواست دوباره با روابط معتبر همان کاربر تطبیق داده می‌شود؛ کوکی دستکاری‌شده یا رابطه لغوشده scope ایجاد نمی‌کند.
- برای نماینده، `accessiblePartyIds` فقط شامل Party فعال است؛ فهرست همه مجوزها به‌صورت جدا در `representedParties` نگهداری می‌شود.
- دسترسی مستقیم به شناسه متعلق به شرکت دیگری توسط `canAccessParty` رد می‌شود.
- اختیار امضا علاوه بر Party فعال، همچنان به رابطه مستقل `AUTHORIZED_SIGNATORY` نیاز دارد.
- مالک Asset مشتری از `actingPartyId` معتبر در server مشتق می‌شود و `ownerId` خام client منبع مالکیت نیست.

## ۳. رابط کاربری

در هدر پنل نماینده، انتخاب‌گر «شرکت طرف فعالیت» اضافه شد:

- اگر چند شرکت تحت نمایندگی باشد، نماینده می‌تواند بین آن‌ها جابه‌جا شود.
- اگر شرکت انتخاب نشده باشد، dialog انتخاب به‌صورت اجباری باز می‌شود.
- نام شرکت فعال در هدر نمایش داده می‌شود.
- تغییر شرکت باعث reload کنترل‌شده می‌شود تا cache و state صفحات شرکت قبلی باقی نماند.
- اگر نمایندگی فعالی وجود نداشته باشد، پیام روشن نمایش داده می‌شود و منوهای party-scoped مخفی می‌مانند.
- داشبورد تفاوت «فاقد نمایندگی» و «دارای نمایندگی ولی فاقد انتخاب فعال» را نمایش می‌دهد.

## ۴. API انتخاب Party

| مسیر | متد | کاربرد |
|---|---|---|
| `/api/customer/acting-party` | `GET` | دریافت Party فعال و شرکت‌های مجاز |
| `/api/customer/acting-party` | `POST` | انتخاب صریح شرکت و ثبت AuditLog |
| `/api/customer/acting-party` | `DELETE` | پاک‌کردن context فعال |

payload انتخاب فقط شامل `actingPartyId` است و schema سخت‌گیرانه Zod فیلدهای اضافی یا شناسه خالی را رد می‌کند.

## ۵. دامنه APIهای scope‌شده

تعریف جدید `accessiblePartyIds` بدون تغییر قرارداد response موجود، این خانواده‌ها را برای نماینده به Party فعال محدود می‌کند:

- داشبورد مشتری؛
- درخواست‌ها و مدارک؛
- نیروگاه‌ها، کنتورها و قرائت‌ها؛
- پیشنهادها؛
- قراردادها و امضا؛
- تسویه‌ها؛
- اسناد مالی و PDF؛
- پرداخت‌ها؛
- اطلاعات Party.

## ۶. معیار خروج

- [x] نماینده شرکت را به‌صورت صریح انتخاب می‌کند.
- [x] انتخاب فقط از روابط معتبر server-side ممکن است.
- [x] هر درخواست مشتری فقط داده Party فعال را می‌بیند.
- [x] URL یا payload دستکاری‌شده دسترسی به Party دیگر نمی‌دهد.
- [x] تغییر Party، state سمت client را تازه‌سازی می‌کند.
- [x] ثبت Asset مالکیت را از context معتبر مشتق می‌کند.
- [x] انتخاب Party در AuditLog ثبت می‌شود.
- [x] وضعیت‌های بدون نمایندگی و بدون انتخاب فعال هندل شده‌اند.
