# فاز صفر سناریوی ۱۴.۲ - قرارداد دامنه و معیار پذیرش

## ۱. مرجع و هدف

این فاز فقط سناریوی «۱۴.۲؛ شرکت با چند نیروگاه» در سند VPP را تثبیت می‌کند. هدف این است که پیش از migration، API و UI، معنای Party فعال، نمایندگی، قرارداد مادر، برنامه‌های تجاری مستقل، تسویه مستقل و خالص‌سازی قابل اختلاف نباشد.

متن مرجع این نتایج را الزام می‌کند:

1. نماینده مجاز، شرکت را به‌عنوان طرف فعالیت انتخاب می‌کند.
2. دو نیروگاه به‌صورت جدا ثبت می‌شوند و هرکدام مدارک مستقل دارند.
3. یک توافق‌نامه مادر و برای هر نیروگاه یک برنامه تجاری ساخته می‌شود.
4. نیروگاه اول قیمت ثابت و نیروگاه دوم قیمت شاخص بازار دارد.
5. تسویه هر نیروگاه مستقل محاسبه می‌شود.
6. فقط مبالغ تأییدشده مالی و حقوقی وارد یک گروه خالص‌سازی می‌شوند.

## ۲. واژگان قطعی

| واژه | مدل سیستم | معنای اجرایی |
|---|---|---|
| شرکت | `Party(type=COMPANY)` | مالک هر دو نیروگاه و فروشنده قرارداد مادر |
| نماینده | `Party` و کاربر با نقش `CUSTOMER_REPRESENTATIVE` | شخصی که در محدوده رابطه معتبر از طرف شرکت اقدام می‌کند |
| انتخاب طرف فعالیت | `actingPartyId` | شناسه شرکت که کاربر در هر عملیات مشتری انتخاب کرده است |
| مجوز اقدام | `Relationship(type=REPRESENTATIVE)` | اجازه ثبت و پیگیری عملیات غیرامضایی در بازه اعتبار |
| مجوز امضا | `Relationship(type=AUTHORIZED_SIGNATORY)` | اجازه مستقل برای امضای قرارداد از طرف شرکت |
| توافق‌نامه مادر | یک `Contract` | قرارداد واحد با شرکت به‌عنوان SELLER و برقتو به‌عنوان BUYER |
| برنامه تجاری | `CommercialSchedule` | دقیقاً یک برنامه مستقل برای هر Asset در این سناریو |
| تسویه مستقل | `Settlement` | رکورد مجزا برای ترکیب Contract، Asset و دوره |
| گروه خالص‌سازی | `NettingGroup` و چرخه اجرایی آن | تجمیع خروجی‌های تأییدشده بدون حذف ریز هر تسویه |

## ۳. تصمیم‌های دامنه

### ۳.۱ نمایندگی و امضا

- جهت رابطه از Party نماینده به Party شرکت است.
- رابطه فقط وقتی معتبر است که تاریخ اقدام داخل بازه `validFrom` تا `validTo` باشد و شرکت فعال باشد.
- نقش کاربر به‌تنهایی مجوز دسترسی به شرکت ایجاد نمی‌کند.
- رابطه `REPRESENTATIVE` اجازه انتخاب شرکت، ثبت نیروگاه، بارگذاری مدرک و پیگیری پرونده را می‌دهد.
- امضای قرارداد نیازمند رابطه فعال و جداگانه `AUTHORIZED_SIGNATORY` است. داشتن رابطه `REPRESENTATIVE` به‌تنهایی برای امضا کافی نیست.
- `actingPartyId` داده مورد اعتماد client نیست؛ هر API باید آن را با روابط فعال کاربر تطبیق دهد.

### ۳.۲ دو نیروگاه

- هر نیروگاه Asset مستقل با مالک یکسان یعنی شرکت است.
- هر نیروگاه درخواست و مجموعه مدارک مستقل دارد.
- تأیید یا رد مدارک یک نیروگاه نباید وضعیت مدارک نیروگاه دیگر را تغییر دهد.
- ثبت‌کننده و مالک از هم جدا هستند: actor نماینده است، owner شرکت است.

### ۳.۳ قرارداد مادر و برنامه‌ها

- در این سناریو دقیقاً یک Contract به هر دو Asset متصل می‌شود.
- BUYER و SELLER باید Partyهای متفاوت باشند.
- شرکت SELLER اصلی است و هر دو Asset باید متعلق به همان شرکت باشند.
- برای هر Asset دقیقاً یک CommercialSchedule فعال در بازه قرارداد وجود دارد.
- یک schedule از PricingPlan ثابت و schedule دیگر از PricingPlan شاخص بازار استفاده می‌کند.
- تغییر برنامه یک نیروگاه نباید برنامه یا سابقه قیمت‌گذاری نیروگاه دیگر را بازنویسی کند.

### ۳.۴ تسویه و خالص‌سازی

- تسویه برای هر Asset و هر دوره مستقل ساخته و تأیید می‌شود.
- خطای تسویه یک نیروگاه مانع مشاهده یا اصلاح مستقل تسویه نیروگاه دیگر نیست.
- خالص‌سازی فقط روی Settlementهای `CONFIRMED` انجام می‌شود.
- همه ورودی‌ها باید متعلق به همان شرکت، دارای ارز و بازه یکسان و مربوط به حداقل دو Asset متفاوت باشند.
- هر Settlement فقط یک بار می‌تواند وارد یک batch قطعی خالص‌سازی شود.
- تأیید مالی و حقوقی هر دو الزامی و تأییدکنندگان باید دو کاربر متفاوت باشند.
- نتیجه خالص‌سازی snapshot دارد و ریز Settlementهای مبنا همواره قابل مشاهده می‌ماند.
- تا پیش از تکمیل هر دو تأیید، نتیجه پیش‌نویس است و سند مالی یا پرداخت قطعی ایجاد نمی‌کند.

## ۴. قرارداد داده بین UI و API

- context انتخاب‌شده باید `actingPartyId` صریح داشته باشد.
- API فقط Partyهای به‌طور فعال نمایندگی‌شده را می‌پذیرد.
- شناسه مالک Asset از `actingPartyId` معتبر در server مشتق می‌شود و payload خام client منبع مالکیت نیست.
- ساخت قرارداد مادر باید دو `assetId` یکتا و دو schedule متناظر دریافت کند.
- ساخت Settlement همچنان برای هر `assetId` یک عملیات جدا و idempotent است.
- ایجاد batch خالص‌سازی باید کلید idempotency داشته باشد و تکرار آن batch یا مبلغ تکراری نسازد.

## ۵. موارد خارج از فاز صفر

- migration و تغییر Prisma schema در فاز ۱.
- UI مدیریت نمایندگی در فاز ۲.
- انتخاب‌گر Party فعال و scope شدن APIها در فاز ۳.
- ثبت عملی دو نیروگاه و مدارک در فاز ۴.
- ساخت قرارداد مادر چندنیروگاهی در فاز ۵.
- تولید تسویه‌های مستقل در فاز ۶.
- موتور و گردش تأیید خالص‌سازی در فاز ۷.
- سند مالی، پرداخت و نمای فروشنده در فاز ۸.

## ۶. شکاف‌های فعلی که باید در فازهای بعد بسته شوند

1. کاربر نماینده seedشده به هیچ Party شرکتی متصل نیست.
2. UI/API برای ایجاد و مدیریت Relationship وجود ندارد.
3. context انتخاب Party فعال وجود ندارد و مسیر فعلی فقط حالت یک Party در دسترس را تحمل می‌کند.
4. authorization فعلی رابطه `REPRESENTATIVE` را برای دسترسی عمومی Party می‌پذیرد، اما مجوز مستقل امضا را enforce نمی‌کند.
5. مدل NettingGroup فقط تنظیمات گروه را نگه می‌دارد و batch، item، snapshot و تأیید دوگانه ندارد.
6. صفحه netting فعلی عملیاتی نیست.
7. تسویه مستقل Asset موجود است، اما قید دقیق ماه تقویمی و پوشش کامل قرائت هنوز باید در فاز ۶ enforce شود.
