# گزارش فاز شش سناریوی ۱۴.۲ - تسویه‌های مستقل نیروگاه‌ها

## ۱. نتیجه

برای هر نیروگاه قرارداد مادر، تسویه ماهانه جداگانه و idempotent ساخته می‌شود. قرارداد و ماه مشترک‌اند، اما Asset، برنامه تجاری، نرخ‌نامه، قرائت‌ها، snapshot محاسبه، مبلغ و گردش بررسی هر تسویه مستقل باقی می‌مانند.

## ۲. قرارداد دوره ماهانه

- بازه تسویه به‌صورت نیمه‌باز تعریف شد: ساعت صفر UTC روز اول ماه تا ساعت صفر UTC روز اول ماه بعد.
- API بازه‌های شناور، چندماهه یا شروع‌شده از میانه ماه را رد می‌کند.
- UI به‌جای دو تاریخ آزاد، یک ورودی ماه دارد و بازه استاندارد را تولید می‌کند.
- در این نسخه فقط CommercialSchedule با چرخه `MONTHLY` قابل تسویه است.
- مدل قیمت از schedule همان ترکیب `contractId + assetId` گرفته می‌شود و client نمی‌تواند نرخ‌نامه نیروگاه دیگر را تزریق کند.

## ۳. پوشش قرائت

- فقط قرائت‌های `ACCEPTED` همان Asset و هم‌پوشان با ماه بررسی می‌شوند.
- اولین قرائت باید از ابتدای ماه آغاز و آخرین قرائت در ابتدای ماه بعد تمام شود.
- بین قرائت‌ها نباید شکاف یا هم‌پوشانی وجود داشته باشد.
- قرائت خارج از مرز ماه و قرائت پذیرفته‌شده فاقد انرژی پذیرفته‌شده رد می‌شود.
- خطای پوشش یک نیروگاه پیش از transaction رخ می‌دهد و روی تسویه یا پرونده نیروگاه دیگر اثری ندارد.

## ۴. استقلال و idempotency

- کلید طبیعی نسخه اول تسویه از `contractId + assetId + periodStart + periodEnd + version` تشکیل شده و در دیتابیس یکتا است.
- تکرار درخواست همان نیروگاه و ماه، تسویه موجود را با `idempotentReplay=true` برمی‌گرداند.
- Settlement، SettlementReading و AuditLog در یک transaction ساخته می‌شوند.
- وضعیت Request فقط برای `assetId` همان تسویه به `SETTLEMENT_PENDING` و سپس `SETTLED` می‌رود؛ پرونده نیروگاه دوم تغییر نمی‌کند.
- snapshot شامل نسخه قرارداد، schedule، PricingPlan، شاخص بازار، تنظیم مالی و تمام قرائت‌های مبنا است.
- قیمت ثابت و شاخص بازار از مسیرهای محاسبه مستقل عبور می‌کنند؛ نبود شاخص بازار فقط تسویه نیروگاه شاخصی را متوقف می‌کند.

## ۵. رابط کاربری

- فقط قراردادهای فعال دارای نیروگاه در فرم محاسبه نمایش داده می‌شوند.
- پس از انتخاب قرارداد، فقط نیروگاه‌های همان قرارداد قابل انتخاب‌اند.
- انتخاب نرخ‌نامه دستی حذف شد؛ نرخ‌نامه همیشه server-side از برنامه تجاری همان نیروگاه گرفته می‌شود.
- برای قرارداد چندنیروگاهی، UI صریحاً کاربر را به محاسبه جداگانه نیروگاه دوم هدایت می‌کند.
- بازیابی idempotent از ایجاد جدید در پیام نتیجه قابل تشخیص است.
- نام نیروگاه در فهرست تسویه‌های مدیر کنار شماره قرارداد نمایش داده می‌شود.

## ۶. migration و داده‌های موجود

Migration زیر روی دیتابیس محلی اعمال شد:

`20260914190000_scenario_14_2_independent_settlements`

این migration فقط index مناسب واکشی قرائت‌های Asset، وضعیت و بازه را اضافه می‌کند و داده‌ای را تغییر یا حذف نمی‌کند. دو تسویه آزمایشی قدیمی دارای بازه غیرتقویمی در دیتابیس محلی حفظ شدند؛ قانون ماه تقویمی فقط بر درخواست‌های جدید اعمال می‌شود. در دیتابیس پاک سناریوی پذیرش، چنین داده تاریخی وجود نخواهد داشت.

Seed تغییر نکرده و همچنان فقط هشت کاربر نقش‌ها را ایجاد می‌کند.

## ۷. پوشش آزمون

- پذیرش دقیق یک ماه تقویمی و رد بازه شناور؛
- محاسبه صحیح انتهای ماه در سال کبیسه؛
- پذیرش پوشش پیوسته چند قرائت؛
- رد شکاف و هم‌پوشانی قرائت‌ها؛
- کنترل scope شدن تغییر وضعیت Request به Asset همان تسویه؛
- کنترل وجود index جدید در schema و migration؛
- typecheck، lint هدفمند، تست‌های کامل پروژه، build تولیدی و runtime Next.js.
