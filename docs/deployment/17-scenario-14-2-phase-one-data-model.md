# گزارش فاز یک سناریوی ۱۴.۲ - مدل داده و migration

## دامنه اجرا

فاز یک قرارداد دامنه تثبیت‌شده در فاز صفر را به schema قابل استقرار تبدیل کرد. این مرحله UI مدیریت نماینده، انتخاب Party فعال، ساخت قرارداد مادر و موتور خالص‌سازی را پیاده نمی‌کند؛ این رفتارها متعلق به فازهای بعد هستند.

## تغییرات نمایندگی

مدل `Relationship` اکنون علاوه بر نوع و بازه اعتبار، این اطلاعات را دارد:

- وضعیت فعال یا لغوشده؛
- مرجع اختیار یا وکالت؛
- یادداشت محدود؛
- کاربر ایجادکننده؛
- کاربر و زمان لغو؛
- زمان آخرین تغییر؛
- index مناسب برای واکشی روابط فعال نماینده و شرکت؛
- uniqueness برای جلوگیری از ثبت دوباره همان رابطه در همان تاریخ شروع.

رابطه `REPRESENTATIVE` و `AUTHORIZED_SIGNATORY` مستقل باقی مانده‌اند. لایه احراز هویت فقط روابط فعال و داخل بازه اعتبار را می‌خواند. نماینده برای امضای قرارداد شرکت باید هم دسترسی نمایندگی و هم اختیار امضای مستقل داشته باشد.

قیود دیتابیس، پایان اعتبار قبل از شروع و وضعیت لغوشده بدون زمان لغو را رد می‌کنند. جلوگیری از رابطه یک Party با خودش در application validation فاز دو enforce می‌شود؛ MySQL استفاده هم‌زمان ستون foreign key دارای referential action را در CHECK مربوطه نمی‌پذیرد.

## اتصال برنامه تجاری به نیروگاه

`CommercialSchedule.assetId` از یک شناسه بدون قید به foreign key واقعی `Asset` تبدیل شد. در نتیجه:

- schedule نمی‌تواند برای Asset ناموجود ساخته شود؛
- queryهای برنامه تجاری هر نیروگاه index مستقل دارند؛
- ساختار «یک قرارداد مادر و برنامه مستقل هر نیروگاه» در سطح رابطه داده قابل پیاده‌سازی است.

## مدل اجرایی خالص‌سازی

### NettingBatch

هر اجرای خالص‌سازی یک batch با شماره و idempotency key یکتا است و این موارد را نگه می‌دارد:

- گروه، دوره و ارز؛
- وضعیت `DRAFT`، `FINANCIAL_REVIEW`، `LEGAL_REVIEW`، `APPROVED`، `POSTED`، `REJECTED` یا `CANCELLED`؛
- مجموع دریافتنی، پرداختنی و مبلغ خالص با `Decimal(24,0)`؛
- snapshot محاسبه؛
- actor ایجادکننده و زمان‌های ارسال، تأیید و ثبت نهایی؛
- دلیل رد محدودشده به ۵۰۰ نویسه.

دیتابیس ترتیب دوره، نامنفی‌بودن مبالغ و برابری مبلغ خالص با دریافتنی منهای پرداختنی را کنترل می‌کند.

### NettingItem

هر item یک Settlement و snapshot تغییرناپذیر آن را به batch متصل می‌کند. ترکیب batch و Settlement یکتا است. `eligibilityLockKey` رزرو هم‌زمان Settlement را ممکن می‌کند و uniqueness آن جلوی ورود هم‌زمان یک Settlement به دو batch را می‌گیرد. در رد یا لغو، lock آزاد و زمان آزادسازی ثبت می‌شود.

### NettingApproval

تأیید مالی و حقوقی به‌صورت دو رکورد مستقل با reviewer، تصمیم، یادداشت و زمان نگهداری می‌شوند. برای هر batch حداکثر یک تصمیم مالی و یک تصمیم حقوقی وجود دارد. متفاوت‌بودن دو reviewer در policy دامنه تثبیت شده و در API فاز هفت داخل transaction enforce خواهد شد.

## migration و سازگاری داده

- migration: `20260914130000_scenario_14_2_data_model`
- نوع تغییر: افزایشی و بدون حذف جدول یا داده موجود
- دیتابیس آزمایش‌شده: MySQL 8.4.3
- preflight: صفر schedule یتیم، صفر رابطه با بازه نامعتبر و صفر رابطه تکراری
- وضعیت: migration روی دیتابیس محلی اعمال و Prisma Client بازتولید شد

اجرای اول migration به‌علت محدودیت MySQL برای CHECK روی ستون foreign key متوقف شد. تمام اشیای خالی همان اجرای ناموفق به‌صورت دقیق rollback، رکورد Prisma به‌عنوان rolled back ثبت و نسخه اصلاح‌شده با موفقیت از ابتدا اعمال شد. هیچ داده قبلی حذف یا reset نشد.

## seed

seed تغییری نکرده و همچنان فقط هشت کاربر نقش‌ها را ایجاد می‌کند. هیچ Party، Relationship، Asset، Contract، Settlement یا NettingGroup به داده اولیه اضافه نشده است.

## محدودیت عملیاتی محیط

اسکریپت backup پیش از migration فراخوانی شد، اما executable مربوط به `mysqldump` روی میزبان نصب نیست. migration افزایشی پس از preflight اجرا شد. پیش از staging یا production باید MySQL client نصب و backup/restore drill اجرا شود.
