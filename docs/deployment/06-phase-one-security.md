# فاز ۱ — امنیت پایه و کنترل دسترسی

وضعیت: پیاده‌سازی‌شده و آماده بازبینی تیمی

## کنترل‌های پیاده‌سازی‌شده

- احراز هویت همه APIهای کسب‌وکاری و تازه‌سازی وضعیت کاربر از پایگاه داده در هر درخواست؛ کاربر حذف‌شده یا غیرفعال با JWT قدیمی دسترسی ندارد.
- RBAC متمرکز برای نقش‌های داخلی، مشتری، تأمین، فنی، حقوقی و مالی.
- کنترل مالکیت داده برای مشتری و نماینده مشتری بر مبنای `partyId` در درخواست‌ها، دارایی‌ها، قراردادها، پیشنهادها، قرائت‌ها، تسویه‌ها، صورتحساب‌ها و اسناد.
- محافظت server-side از مسیرهای `/admin` و `/customer` و هدایت نقش نامعتبر به ناحیه مناسب.
- رد درخواست mutation از origin بین‌سایتی و پاسخ `401/403` استاندارد برای API.
- انتقال upload جدید از `public/` به storage خصوصی و ارائه فایل فقط از endpoint احراز هویت‌شده؛ دسترسی مستقیم legacy به `/uploads/*` مسدود است.
- محدودیت نوع و اندازه فایل، نام‌گذاری امن فایل و هدر `nosniff` در دانلود.
- هدرهای امنیتی پایه و `no-store` برای پاسخ API.
- عدم بازگرداندن مدل کامل User در relationهای reviewer و audit.
- منع seed در production، حذف رمز ثابت seed و الزام رمز توسعه‌ای حداقل ۱۲ کاراکتر.
- الزام `NEXTAUTH_SECRET` حداقل ۳۲ کاراکتر در production.

## شواهد پذیرش

- `npm run typecheck`: موفق.
- lint هدفمند برای فایل‌های امنیت، layoutها و کل API: موفق.
- `npm run test:security`: سه تست، سه موفق.
- `/_next/mcp/get_compilation_issues`: بدون خطای compilation.
- مرورگر مهمان برای `/admin/dashboard` به `/login` هدایت شد.
- مرورگر مهمان برای `/api/dashboard` پاسخ `401` دریافت کرد.
- دسترسی مستقیم به `/uploads/security-probe.pdf` پاسخ `404` دریافت کرد.
- Next.js runtime: بدون config error و session error.

## مواردی که پیش از production هنوز باید تکمیل شوند

- rate limiting توزیع‌شده برای login و API بر پایه زیرساخت انتخابی (Redis/WAF/API Gateway).
- ثبت رخدادهای امنیتی ناموفق با IP و user-agent در sink مرکزی، بدون داده حساس.
- malware scanning و object storage خصوصی با URL زمان‌دار برای اسناد واقعی.
- CSP مبتنی بر nonce پس از تعیین reverse proxy و سیاست assetها.
- چرخش secretها و آزمون revoke کردن نشست‌ها در staging.
- اجرای integration test ماتریس نقش × endpoint با MySQL ایزوله.

این موارد زیرساختی مانع تلقی‌شدن کد فعلی به‌عنوان production-ready کامل هستند و باید در فازهای زیرساخت، مشاهده‌پذیری و آزمون نهایی بسته شوند.
