# گزارش اجرای فاز شش: پرداخت، پیش‌بینی نسخه‌دار و یکپارچگی داده

## دامنه

این فاز سناریوی `AC-06`، نیازمندی `PR-11` و بخش قابل اجرای `OPS-03` تا `OPS-05` را پوشش می‌دهد. خالص‌سازی `AC-07` عمداً خارج از این فاز است و تا فاز هفت و فعال‌شدن feature flag خاموش می‌ماند.

## پرداخت و تخصیص

- صفحه demo پرداخت با داده واقعی API جایگزین شد.
- پرداخت مستقل از صورتحساب، با مرجع بانکی، مبلغ صحیح IRR، ثبت‌کننده و کلید idempotency ثبت می‌شود.
- گردش پرداخت `PENDING -> CONFIRMED | REJECTED` است و تخصیص فقط پس از تأیید ممکن است.
- یک پرداخت می‌تواند به چند صورتحساب و یک صورتحساب از چند پرداخت تخصیص بگیرد.
- مبلغ تخصیص در `DECIMAL(24,0)` ذخیره می‌شود؛ مانده پرداخت و صورتحساب با `decimal.js` کنترل می‌شود.
- تخصیص بیشتر از مانده پرداخت یا صورتحساب و تخصیص با ارز متفاوت رد می‌شود.
- `allocationVersion` روی Payment و Invoice رقابت هم‌زمان را با optimistic concurrency کنترل می‌کند.
- ایجاد تخصیص، به‌روزرسانی مانده‌ها، وضعیت Invoice و وضعیت Settlement در یک transaction انجام می‌شود.
- Invoice در تخصیص جزئی `PARTIALLY_PAID` و پس از تکمیل `PAID` می‌شود؛ Settlement فقط بعد از پرداخت کامل `PAID` می‌شود.
- تغییر مستقیم Invoice به وضعیت‌های پرداختی حذف شد؛ این وضعیت‌ها فقط خروجی تخصیص هستند.
- ثبت و تخصیص تکراری با کلید یکسان اثر مالی دوباره ایجاد نمی‌کند.

## نسخه‌بندی پیش‌بینی تولید

- جدول immutable با نسخه مستقل سالانه و دوازده مقدار ماهانه اضافه شد.
- هر نسخه منبع، روش، جمع سالانه، سازنده، زمان ارسال، تأییدکننده و زمان تأیید دارد.
- گردش نسخه `DRAFT -> REVIEW -> APPROVED` است؛ تأیید فقط برای نقش فنی، مدیر یا ادمین مجاز است.
- با تأیید نسخه جدید، نسخه تأییدشده قبلی همان Asset/سال `SUPERSEDED` می‌شود.
- ارسال فرم کامل نیروگاه یک نسخه `REVIEW` قابل ممیزی ایجاد می‌کند.
- پیش‌بینی‌های قدیمی با migration به نسخه اولیه منتقل شدند.
- صفحه جزئیات دارایی مشتری از داده demo خارج و به Asset واقعی و تاریخچه نسخه‌ها متصل شد.

## backup و restore

- `npm run db:backup -- backups/<name>.sql` از `mysqldump --single-transaction` استفاده می‌کند.
- رمز دیتابیس در آرگومان process قرار نمی‌گیرد و از محیط child process عبور داده می‌شود.
- backup production به تأیید صریح `ALLOW_PRODUCTION_BACKUP=true` نیاز دارد.
- `npm run db:restore:verify -- <backup.sql>` فقط با `ALLOW_RESTORE=true` اجرا می‌شود.
- مقصد restore باید `RESTORE_DATABASE_URL` جدا باشد و اسکریپت از restore روی دیتابیس مبدأ جلوگیری می‌کند.
- بعد از restore تعداد migrationهای کامل، Partyها و Audit Logها بررسی می‌شود.
- فایل ناقص در شکست backup باقی نمی‌ماند.

در میزبان فعلی `mysqldump` و `mysql` نصب یا در PATH نیستند؛ بنابراین fail-safe اسکریپت آزموده شد اما تمرین واقعی restore انجام نشد. نصب MySQL Client و فراهم‌کردن دیتابیس جداگانه staging برای بسته‌شدن `OPS-05` الزامی است.

## محدودیت‌های باقی‌مانده

- `D-006`: ستون‌های جدید پرداخت Decimal هستند، ولی تبدیل همه ستون‌های مالی قدیمی Settlement از Float هنوز نیازمند scale مصوب است.
- `D-019`: پرداخت دستی پیاده شده؛ وضعیت تصمیم باید توسط مالی تصویب شود.
- `D-021`: تا تصویب RPO/RTO و اجرای restore drill روی staging، آمادگی بازیابی کامل نیست.
- گزارش trace مستقل Workspace همچنان به تصمیم `D-016` وابسته است؛ ردیابی Party/Contract/Asset/Period از مسیر Invoice و Settlement برقرار است.
